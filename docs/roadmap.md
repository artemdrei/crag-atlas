# Roadmap

Порядок реалізації, узгоджений з дизайном (Design canvas). Кожен пункт —
окремий вертикальний зріз: статичний UI (common/desktop/mobile) → підключення
до `apps/api` (поки на статичному JSON, не Supabase — див.
`docs/domain.md`) → готово, перехід до наступного.

Дизайн-система: структура токенів (palette/typography), кольори — свій
акцент під клаймінг-тему.

## Ролі

Три рівні доступу, закладаються через `ProtectedRoute` + auth-заглушку з
першого дня (див. "Фундамент"), навіть без реальної авторизації:

- **Незареєстрований юзер (гість)** — читає публічний контент: регіони,
  сектори, маршрути, топо, медіа. Без ticks/логбука/коментарів.
- **Зареєстрований юзер** — все, що гість, плюс: відмітити пролаз, логбук,
  профіль, налаштування, коментарі, голосування за категорію.
- **Адмін** — все, що зареєстрований юзер, плюс: адмін-редактор (сектор/
  маршрут, чернетка/публікація).

## Фундамент (один раз, до будь-якої фічі)

1. **Router-скелет фіналізується першим** — маршрути (`ROUTES`), layout-
   обгортки desktop/mobile вже є в коді, перша реальна сторінка (п.2)
   підключається через них, не в обхід.
2. **Auth-заглушка одразу**, реальної авторизації ще нема. `UserProvider`
   (поки фейковий перемикач ролі: гість/юзер/адмін) + `ProtectedRoute`.
   Коли підключимо реальний Supabase Auth — міняється тільки всередині
   провайдера, роутинг і сторінки не чіпаються.
3. **API contract-first як звичка.** Для кожної сторінки: спершу бекенд-
   модуль з контрактом (DTO), потім фронт під нього.
4. **Apex-домен vs продукт — рішення зараз, реалізація пізніше.** "Лендінг"
   (вибір регіону, п.2) — домашня сторінка продукту на сабдомені, не
   маркетинговий сайт. Справжній маркетинговий `apps/website` на
   apex-домені створюється окремо, коли дійде черга — не зараз.

## Сторінки (кожна для desktop і mobile окремо)

1. Дизайн-система (токени, кольори, типографіка)
2. Лендінг / вибір регіону ("Куди лізеш?") — доступно гостю
3. Сторінка регіону (список секторів) — доступно гостю
4. Сторінка сектора (топо + список маршрутів) — доступно гостю
5. Сторінка маршруту (бета, відео, коментарі, мої пролази) — перегляд
   доступний гостю, коментарі/пролази — тільки зареєстрованому
6. Відмітити пролаз (форма Tick) — тільки зареєстрований юзер
7. Логбук — тільки зареєстрований юзер
8. Профіль — тільки зареєстрований юзер
9. Налаштування профілю — тільки зареєстрований юзер
10. Гостьовий режим (без акаунта) — окремо перевірити UX для незалогіненого
11. Адмін-редактор (сектор/маршрут, чернетка/публікація) — тільки адмін
12. Карта (мобайл, низький пріоритет)

Поза скоупом зараз: Garmin-інтеграція — окрема історія, не чіпаємо.

## Цикл на кожну сторінку (2–11)

1. Бекенд: DTO + endpoint (на статичному JSON) — контракт фіксується.
2. Фронт: `common/desktop/mobile` під цей контракт, підключення до
   реального router.
3. Якщо сторінка потребує ролі вище гостя — одразу обгортається в
   `ProtectedRoute` з auth-заглушкою відповідної ролі.
4. Наступний пункт roadmap.

## Мислення на рівні віджетів

Повторювані елементи UI (навігація/меню, breadcrumbs, таби, хедер, фільтри)
пишуться один раз як переюзабельні компоненти, а не копіюються по сторінках.

- **Обов'язкове меню/навігація** (десктоп-сайдбар, мобайл bottom nav +
  header) — консистентне, розширюється/звужується по кількості пунктів без
  переписування, живе в `app/desktop/layout` / `app/mobile/layout`.
- **Breadcrumbs, таби, фільтри** — генеричні, не привʼязані до конкретної
  сторінки → `shared/ui`.
- **Складені блоки з кількох фіч** (напр. права панель з кількома табами) →
  `widgets/<name>` — лише коли справді збирає кілька фіч разом, не для
  одного простого списку.
- Правило: перш ніж писати новий UI-елемент для конкретної сторінки —
  перевірити, чи він насправді специфічний для неї, чи це вже другий/третій
  випадок того самого патерна (меню, таби, фільтр) — тоді виносити в
  `shared/ui`/`widgets` одразу, а не після третього дублювання.

## Правило прийняття фундаментальних рішень

Коли постає питання "як це організувати" (роутинг, шар компонента, auth,
структура папки) — рішення приймається один раз і фіксується тут
(`docs/roadmap.md`) або в `CLAUDE.md`, а не вигадується заново щоразу, коли
з'являється схожа сторінка чи фіча.
